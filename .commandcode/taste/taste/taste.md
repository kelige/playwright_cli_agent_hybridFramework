# Taste
- Wants the project's MCP/context spec document consulted and changes validated against it before edits are applied (halted planned work to have the context file re-checked first). Confidence: 0.6
- Prefers to hand over app behavior by walking through one complete flow himself in a live, monitored/recording browser that the agent launches, instead of describing the flow in text. Confidence: 0.6
- In multi-role apps, wants the work done strictly one role at a time: close the session, relaunch for the next role, and record/accumulate prompts from start to end per role rather than batching roles together. Confidence: 0.7
- Wants UI/web test prompts and API test prompts kept in separate documents, with the API document following the format of a reference prompts file he provides, rather than mixed into one file. Confidence: 0.6
- Treats base URLs, tenant names and tenant data as environment configuration, not constants: the product is multi-tenant (any number of universities, each on its own URL) with an identical workflow and differing data, so docs/tests must never hard-code the tenant URL or its data and must read them from `.env`/test data. Confidence: 0.75
- Expects `.env` to hold only the base URL and the admin account: because provisioning is RBAC-gated, the agent must create every other role account itself at runtime (capture the generated temporary password, then set it to the team's standard password) instead of asking for all role credentials up front. Confidence: 0.7
- Wants generated reference artifacts (routes, API/DB prompts, JSON schemas) grounded in the real running project — live-captured API traffic and the read-only project SQLite database — and rejects carrying over templates or schemas from an unrelated ecommerce project or assuming what "developers would provide". Confidence: 0.65
- Wants every deliverable file (web prompt, API prompt, routes, schemas, DB prompt) filled in with real per-role content covering the whole role chain from first role to last, not partially populated or placeholder sections; when a run stops early or a later capture reveals more, expects the earlier files to be revisited and backfilled ("add information if you forget in old files") rather than left stale. Confidence: 0.7
- Objects to silently overwriting pre-existing files: when a file already existed before the request, expects the agent to preserve/append to the existing content (or ask first) and to state plainly whether a write replaced it. Confidence: 0.6
- When a freshly live-verified artifact replaces an older draft, wants only the best/current version kept and the superseded files deleted — not preserved as legacy copies or offered for archival ("keep best, delete not required"), and this applies to the whole set of stale duplicate prompt/reference files, not just the one being edited; his objection is to *silent* overwriting, not to dropping stale content. Confidence: 0.7
- When he supplies a reference document that contains a section (e.g. a web testing architecture), expects that section reproduced inline in the deliverable itself — a pointer such as "follow the context file" for the HOW is not enough, because the reference file already spells it out. Confidence: 0.6
- Rejects speculative scaffolding: don't create folders/placeholder specs/starter files first "so we have structure" — work must follow the documented flow in order (analyze the live page, then page object, then fixture, then test data, then the spec), so nothing is written before the live analysis it depends on. Confidence: 0.65
- Wants Playwright runs executed headed (visible browser) rather than headless, so he can watch the suite drive the real app. Confidence: 0.6
- Expects the agent to carry the full set of accumulated requirements across interruptions (breaks, pauses, session resumes) without being re-told, and to hold/restate them before continuing. Confidence: 0.55
