# Taste
- Wants the project's MCP/context spec document consulted and changes validated against it before edits are applied (halted planned work to have the context file re-checked first). Confidence: 0.6
- Prefers to hand over app behavior by walking through one complete flow himself in a live, monitored/recording browser that the agent launches, instead of describing the flow in text ("give live monitoring, I will show how to create a new university"). Confidence: 0.7
- In multi-role apps, wants the work done strictly one role at a time: close the session, relaunch for the next role, and record/accumulate prompts from start to end per role rather than batching roles together. Confidence: 0.7
- Wants UI/web test prompts and API test prompts kept in separate documents, with the API document following the format of a reference prompts file he provides, rather than mixed into one file. Confidence: 0.6
- Treats base URLs, tenant names and tenant data as environment configuration, not constants: the product is multi-tenant (any number of universities, each on its own URL) with an identical workflow and differing data, so docs/tests must never hard-code the tenant URL or its data and must read them from `.env`/test data. Confidence: 0.75
- Expects `.env` to hold only the base URL and the admin account: because provisioning is RBAC-gated, the agent must create every other role account itself at runtime (capture the generated temporary password, then set it to the team's standard password) instead of asking for all role credentials up front. When role credentials *are* supplied, they win — resolve credentials as "use provided role creds if present, else fall back to the admin-provisioned account", never require the full set up front. Confidence: 0.7
- Never hands back a "you do this now" list for configuration: when something needed to run looks missing (DB host/name/user/password in `.env`), expects the agent to investigate the repo itself (existing env vars, docker/compose files, docs, the read-only SQLite snapshot) and fill in whatever can be filled safely — "you only fill those details yourself" — only surfacing what genuinely cannot be discovered and stating what it used instead. Confidence: 0.7
- Wants generated reference artifacts (routes, API/DB prompts, JSON schemas) grounded in the real running project — live-captured API traffic and the read-only project SQLite database — and rejects carrying over templates or schemas from an unrelated ecommerce project or assuming what "developers would provide". Confidence: 0.65
- Wants every deliverable file (web prompt, API prompt, routes, schemas, DB prompt) filled in with real per-role content covering the whole role chain from first role to last, not partially populated or placeholder sections; when a run stops early or a later capture reveals more, expects the earlier files to be revisited and backfilled ("add information if you forget in old files") rather than left stale. Confidence: 0.7
- Objects to silently overwriting pre-existing files: when a file already existed before the request, expects the agent to preserve/append to the existing content (or ask first) and to state plainly whether a write replaced it. Confidence: 0.6
- When a freshly live-verified artifact replaces an older draft, wants only the best/current version kept and the superseded files deleted — not preserved as legacy copies or offered for archival ("keep best, delete not required"), and this applies to the whole set of stale duplicate prompt/reference files, not just the one being edited; his objection is to *silent* overwriting, not to dropping stale content. Confidence: 0.7
- When he supplies a reference document that contains a section (e.g. a web testing architecture), expects that section reproduced inline in the deliverable itself — a pointer such as "follow the context file" for the HOW is not enough, because the reference file already spells it out. Confidence: 0.6
- Rejects speculative scaffolding: don't create folders/placeholder specs/starter files first "so we have structure" — work must follow the documented flow in order (analyze the live page, then page object, then fixture, then test data, then the spec), so nothing is written before the live analysis it depends on. Confidence: 0.65
- Wants Playwright runs executed headed (visible browser) rather than headless, so he can watch the suite drive the real app — including the all-roles test-case command ("i want npm run testcases it should run headed mode"). Confidence: 0.7
- Prefers a whole workflow's tests consolidated into a single spec file rather than split across many small spec files, and expects the matching npm script (`test:db`, `test:smoke`, etc.) to actually run the complete suite for that project/tag. Confidence: 0.55
- Defines the smoke suite by breadth of business coverage, not by a couple of login checks: `@smoke` must exercise the application's major functionality, meaning every role in the matrix plus at least one end-to-end workflow completed start to finish (across web/API/DB layers). Confidence: 0.8
- Wants one terminal command that runs a complete end-to-end workflow across the whole app, and if the flow hits a real-world step (camera, face enrollment, biometric capture) the run must open a live visible browser and pause/wait until the human completes enrollment or the app emits the capture-complete event — no faking or stubbing hardware steps. Confidence: 0.65
- A human-in-the-loop step is a pause, not a stop: the moment he completes the manual action (e.g. face enrolled) the run must detect that and continue on its own — an unbounded wait that only trusts one completion signal, or keeps waiting after the dialog says success, is a bug ("once the face enrolled the process need to continue", "wait till face enrolled after enrolled continue automation"). No artificial timeouts on these waits by default. Confidence: 0.7
- "Waiting" is only acceptable for something the app itself must do: if a blocking prompt is something the automation can click (e.g. an "Evaluator guidance / Go to task" dialog, a Refresh after success), he expects the agent to find the blocking screen, clear it and drive the flow on — not to report that the run is waiting and ask him to intervene. Confidence: 0.6
- Does not accept an end-to-end workflow test that stops at a mid-flow waypoint (e.g. "opens the marking workspace"): each actor must perform its real business action and the chain must be asserted through to the terminal outcome (evaluator marks and submits the script itself, moderation done, report forwarded and received by Admin). Confidence: 0.6
- Expects the agent to carry the full set of accumulated requirements across interruptions (breaks, pauses, session resumes) without being re-told, and to hold/restate them before continuing. Confidence: 0.55
- Separates concerns strictly: the end-to-end workflow must be one continuous flow with no test cases inside it, while test cases live in their own per-role artifacts (one doc file per role, one matching Playwright script per role). Confidence: 0.7
- Wants the automated test-case run to never abort on a finding: every observed bug is written to a dedicated bug/defect file and the run continues through the remaining cases and roles to the end. Bugs belong in their own file kept separate from the test cases themselves (he named it `BUG_DVS`). Confidence: 0.8
- All test cases across all roles must be launchable with a single command (one npm script), and that command must tell him where the results are stored — a per-run summary plus per-role report/log locations — rather than requiring one command per role or hunting through folders. Confidence: 0.7
- Prefers easily recognisable, sequential names for generated test entities over random IDs — e.g. universities named `Automation testing -1`, `Automation testing -2`, `… -3` so he can scan and remember them in the console. Confidence: 0.65
- When a run fails, expects the concrete evidence dug out first — the report/screenshot/log line that shows the actual error — and the root cause stated before any code change; speculative edits or repeated blind re-runs are what he is objecting to when he asks "why test has failed", because one workflow must never eat hours. Confidence: 0.6
- Rejects forcing past a gate the app itself enforces: when submission only opens after the evaluation timer reaches 00:00 and after every script page has been visited (10-page script = 10 pages), the test must genuinely wait out the timer and page through all pages, not dispatch synthetic clicks or poll a disabled button to get through. Confidence: 0.6
- Terminal outcomes of a run must leave a durable, shareable artifact (e.g. the Admin-received report saved per run as HTML/JSON under `reports/`): watching it in a headed browser or reading it in the console is not enough, because he needs to show the result to other people ("I need to show it to others"). Confidence: 0.7
- The end of a full workflow must be a readable checklist/summary page, not console logs: one green tick per completed stage, credentials spelled out under the tick that created them (university name, admin mail, password; then each role's mail + password), the chain running all the way to "Admin received result report", and the last element being a "Click here to view result" link to that run's report — the flow must stop there. Confidence: 0.6
- Wants run results also written as a spreadsheet into the repo's `docs/` folder (CSV or Excel, e.g. `docs/reports/DVS-EVALUATION-REPORT-<runId>.xlsx`), not only HTML/JSON under `reports/`, and wants a way to reopen a previous run's result later ("how I can see report once more") rather than only at the end of the run. Confidence: 0.65
- Report artifacts must be viewable without leaving the editor: a binary-only `.xlsx` that VS Code can't render draws "why am unable to open excel file in vs i want it to view", so every such output should also be emitted as a plain-text CSV he can open directly. Confidence: 0.6
- When a generated artifact isn't openable/viewable for him (an HTML report he can't open, a binary spreadsheet), expects the agent to fix the viewing setup itself — install the needed editor extension (e.g. Live Preview) and add it to `.vscode/extensions.json` — not just hand back a file path. Confidence: 0.6
- Test-case documentation must be a machine-readable spreadsheet deliverable — CSV per role plus a combined Excel workbook — not prose markdown files, and each role needs a substantial set (100–150 cases) that is persona-driven and aimed at production readiness rather than a handful of happy paths. Confidence: 0.75
- Judges a test-case run by completion against the documented inventory, not just pass/fail per role: the summary must state how many of the several hundred documented cases are actually completed (covered by an executable spec) versus still pending, and make the pending backlog reachable ("how many are completed", "at end you need to complete every test cases"). Confidence: 0.75
- Wants defects reported grouped by role at the end of a run — a `role: defects` breakdown listing the defects found per role — rather than only an aggregate defect count or a flat log. Confidence: 0.7
- Wants status explained in short plain language first (a few bullets: what exists, what runs, what is missing) before layered tables, metrics breakdowns and per-role detail; a dense report-style answer to a plain question draws "what are you saying" and must be re-stated simply. Confidence: 0.55
- For large remaining scope, wants the whole thing laid out in one complete written plan before implementation — every remaining case/phase, not an incremental "pick one batch and I'll start" proposal; even when he concedes the staging is sensible ("your wish but"), he still demands the full plan. Confidence: 0.6
- Every test run must end with a per-case result list, not just aggregate counts: each executed test case shown as passed (green tick) or failed with the actual failure reason, so he can see at a glance which cases are green and why the others aren't. Confidence: 0.65
- Test data must look realistic and varied, not a single pristine reference: script marks/outcomes must differ per university/student (some questions left unanswered, partial awards, no one scoring full marks on everything) — "dont give full on marks to all students give differnet marks" — while staying reproducible per run. Confidence: 0.65
- Per-run output folders must stay minimal: only the results report page (with a tick checklist of completed role tasks) and the role credentials — no logs, Playwright HTML/JUnit output, dashboards, Allure/run-state or `.env` copies left behind ("i dont want all these files", "remove all those things"). Debug-retention should be opt-in (e.g. a `--keep-files` flag), not the default. Deliver exactly the number of artifacts he asked for, no extra report/JSON/duplicate summary pages ("why are you again giving all these i asked only three"); cleanup must run per unit of work so leftovers can't accumulate, not only at the very end of a run. Confidence: 0.8
- Corrects any design that treats university credentials as fixed configuration: only the platform link plus the platform admin email/password stay the same — every other credential differs per university, so a static CI/env credential file must hold only the platform section and each build must generate the tenant credentials itself. Confidence: 0.75
- Expects a fresh tenant run (`npm run test:platform`) to start from a clean slate: the previous university's tenant env data (URL, admin and role logins) is cleared so stale values can't be confused with the current tenant, while platform/browser/database configuration is deliberately preserved. Confidence: 0.65
